# [GPT-6-Sol] Audit — ARC-01 — design and quality

## Verdict

**FAIL.** The proposed API can carry an accepted daily quest into the next interval, and `progress_many` can write the same progress record repeatedly in one transaction. Both need resolution before A-G1 accepts the API.

## Findings

| # | Severity | Location | Finding | Evidence / failing scenario | Suggested fix |
|---|---|---|---|---|---|
| 1 | **blocker** | Quest record and progress algorithm (`docs/research/ARC-01-quest-achievement.md:554`) | Acceptance has no interval identity. | `active` is one bit across intervals. Accept a daily contract on day 0 and leave it unfinished; on day 1, progress uses a fresh interval key but still sees `active = true`, bypassing that day’s board draw. The game offers contracts per day (`ref/grimworld/docs/design/14-quests-region-1.md:107`). The specified `accept` checks also omit the current interval’s completed state, so a completed one-off quest can be accepted again and occupy an active slot. | Specify whether acceptance expires at rollover. If it does, store the accepted interval and check it on progress; reject acceptance when that interval is already completed. Add both scenarios as tests. |
| 2 | **blocker** | `progress_many` and cost model (`docs/research/ARC-01-quest-achievement.md:771`) | Batch size is unbounded, and a batch can write one record more than once. | The external ABI accepts an arbitrary `Span`; the stated bound is left to the consumer. Even two *distinct* task entries belonging to one quest run the single-task algorithm twice and write its packed progress record twice. Duplicate entries amplify this. This breaks CAIRO §5’s one-write-per-model rule (`docs/CAIRO.md:68`); the 28-quest “worst case” (`docs/research/ARC-01-quest-achievement.md:1170`) is not a worst case for this entrypoint. The achievement batch has the same issue. | Set and enforce a package-level batch bound; aggregate entries and update each affected record once. Give `progress_many` its own worst-case read, write and event estimates. |
| 3 | **major** | Association layout and Q-14 (`docs/research/ARC-01-quest-achievement.md:648`) | The 28-per-task limit is a lifetime limit, though Q-14 justifies it using *live* quests. | Definitions cannot be removed or redefined, and neither package removes IDs from association pages. After 28 quests have ever used a common task, defining the 29th fails even if all earlier quests have ended. Q-9’s proposed `set_end` would not free a page slot. | Decide at A-G1 how tasks remain usable as the game grows: removal with defined migration rules, versioned task IDs, or an explicitly accepted lifetime cap. Apply the decision to achievements too. |
| 4 | **major** | D-6 and D-7 (`docs/research/ARC-01-quest-achievement.md:333`) | “Locked for ever” overstates two source defects. | A dependent defined after a **recurring** prerequisite’s first completion can be unlocked by its next completion: `create` adds the reverse condition (`ref/arcade/packages/quest/src/component.cairo:178`), and each completion decrements it (`ref/arcade/packages/quest/src/component.cairo:262`). Likewise, a condition naming a not-yet-defined quest can be satisfied if that quest is later defined and completed; duplicate conditions can be satisfied by repeated completions of a recurring prerequisite. The one-off scenarios remain real. | Qualify the source claims and tests by prerequisite recurrence and definition order. Keep the native “already defined” rule as a proposed design choice. |
| 5 | **major** | Workspace manifest proposal (`docs/research/ARC-01-quest-achievement.md:1244`) | The proposed `edition.workspace = true` is outside Scarb’s documented inheritable package keys. | Scarb’s [workspace reference](https://docs.swmansion.com/scarb/docs/reference/workspaces.html) lists supported inherited keys without `edition`; its [manifest reference](https://docs.swmansion.com/scarb/docs/reference/manifest.html) shows `edition = "2024_07"` in each `[package]`. ARC-02 should not copy this manifest as written. | Put `edition = "2024_07"` in each package manifest and verify the manifest with Scarb 2.19.4. |
| 6 | **minor** | Achievement events (`docs/research/ARC-01-quest-achievement.md:1036`) | The achievement event API is abbreviated. | Five variants are given as comments rather than complete typed event structs, despite the brief’s requirement for a signature for every event. Implementers must supply field types, keys and derives. | Specify the full Cairo event structs, as §3.4 does for quests. |
| 7 | **minor** | Unlock view and presence bits (`docs/research/ARC-01-quest-achievement.md:794`) | Two storage semantics are left to the implementer. | The tests expect `quest_is_unlocked` to become true immediately after prerequisites complete, before dependent progress sets the cache; its algorithm is unspecified. Both definition layouts allocate a `defined` bit, but neither public definition struct contains it or says how packing and unpacking handle an empty slot. | Specify that the view checks prerequisites when the cache is false, and define the presence-bit packing and empty-record behavior. |
| 8 | **minor** | Page reads and event estimates (`docs/research/ARC-01-quest-achievement.md:1152`) | Some cost rows undercount or overstate calls. | Reading until `len < 7` takes **two** pages for exactly seven IDs and one page for zero IDs, whereas `⌈N/7⌉` gives one and zero. `progress_many` emits one event **per entry** in event mode, not one per call. Quest `count == 0` returns before emission under §3.5, contrary to “any case: 1 event.” | Correct the page formula and distinguish `progress` from `progress_many` and zero-count calls. |
| 9 | **minor** | Interval signature (`docs/research/ARC-01-quest-achievement.md:575`) | A valid schedule can produce an interval ID that does not fit `u32`. | `start = 0`, `interval = duration = 1`, `end = 0` passes validation. At timestamp `2^32`, `(time − start) / interval` exceeds the specified return type. | Constrain the schedule’s lifetime, use a wider interval ID, or specify overflow behavior and test the boundary. |

## Coverage

I checked more than ten §1–§2 source citations, including D-1 through D-4 and D-5 through D-12, against both Arcade components, models, stores and tests. The four ADR-0004 defects are supported by the cited code. I also reviewed both proposed APIs, every packed bit range, A-1 through A-9, the game’s guild, title and contract rules, access control, cost, workspace and gate questions. All stated packed records fit below `2^251`; I found no specified `u256` use or direct external-ABI bypass of the stated admin, reporter and player checks. The trusted internal layer still requires the consumer’s own checks.

This was a reading audit: I changed no files and ran no builds or tests. Scarb’s documentation was checked online. The registry endpoints were inaccessible to the audit tool, so the report’s claim that both package names are free was **not independently confirmed**; recheck it at A-G1.
